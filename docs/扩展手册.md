# 扩展手册：加维度 / 加 skill / 蒸馏新书

> 这份手册只讲怎么扩。所有操作都在包根目录下执行，改完**必跑** `python tools/dim_check.py`，0 错才算完。

## 先分清三种情形

| 情形 | 什么时候用 | 一条命令能搞定吗 |
|---|---|---|
| A 往已有维度加 skill | 已有维度还想多几件工具 | 不能，手工四步（很快） |
| B 加一个全新维度 | skill 已经写好 / 从别处搬进来 | 能：`new_dimension.py` |
| C 从一本新书蒸馏 | 手上有书，想变成新维度 | 不能，走六步流水线（B 是倒数第二步，**最后一步是整包升级**） |

**默认规则：并入优先。** 一本新书先做「归属勘定」——把书的内容结构逐块对照注册表的「触发信号」列：

1. **与某个已有维度同族**（回答的是同一类问题、用的是同一类方法）→ **并入该维度**：skill 放进该维度，注册表该行的「来源」补上书名、「skill 数」+N；
2. **与所有已有维度都不同族** → **新增维度**（走情形 B/C）。

判断依据是"它回答哪一类问题"，不是书名像不像。**不为凑数硬拆，也不为省事硬合。**

---

## 情形 A：往已有维度加 skill

1. 建目录 `skills/<前缀>-<名字>/`，照 `templates/skill-template/SKILL.md` 写 `SKILL.md`，并写 `test-prompts.json`（三类用例：应该触发 / 不应触发 / 边界）。
2. `dimensions.registry.md` 里该维度的「skill 数」+1。
3. hub 的 H 节该分组下补一行：`| \`<slug>\` | 核心功能 |`。
4. **先装依赖、再自检**（见「收尾」节）：`python tools/install_deps.py --install` → `python tools/dim_check.py`。

## 情形 B：加一个全新维度

```bash
python tools/new_dimension.py --prefix <前缀本体，如 ptolemy；别带结尾的 - 或 *> --name <维度名> --layer <观察|象征|校准> \
    --signals "<触发信号，顿号分隔>" --source "<来源>" --skill <入口skill名> \
    --skill-title "<入口一句话>" --emoji 🧩 \
    [--data 出生信息] [--order 13.5] [--desc "frontmatter 描述"] [--dry-run]
```

命令会依次做：照 `templates/skill-template/` 建 skill 骨架 → 注册表加行 → hub 概览表加行 → hub 的 H 节加分组 → 自动同步描述行里的「观察 N / 象征 M / 校准 K」→ 跑 `tools/dim_check.py`。加完**hub 正文一个字都不用改**。

加完以后自己填空：R 节回书抄原话（带出处）、I/A/E/B、练习手册、反例黑名单、`test-prompts.json`；然后再跑一次自检。

`--dry-run` 只看它要干什么，不落盘。重复加同一个维度会被拒绝（要改就直接编辑注册表那一行）。

### 新维度要不要设「硬闸门」（显式请求才激活）

有些维度**不该靠语义联想激活**——用户没明说要它，就不激活，而且**不显示**。判据是**显式词**，不是泛化词。加这种维度时，四处都要动（缺一不可）：

1. **注册表 `dimensions.registry.md`**：第 16 行那种「触发信号」列写成 `⛔**硬闸门：仅显式请求才激活**` + 显式词表 + 泛化词禁令；并在「## 硬闸门（显式请求才激活的维度）」一节加一行。
2. **该维入口 skill 的「## 触发条件」**：**开头**写 `⛔ 硬闸门（先看这条）`，列出显式词与不算的泛化词，并声明「这条闸门优先于下面的『应该触发』清单」；同时在「不应触发」里补一条泛化词情形。
3. **hub `SKILL.md` 的维度概览表**：与该行同步同一表述（`dim_check` 会对齐）。
4. **不动 hub 的 STEP 1 与输出纪律**：那两处写的是**通则**（先判闸门后算权重；闸门没过**整行不显示**），加维度时不用改。

**行为差别（要记住）**：一般维度权重 0 → **列一行**并注「本轮不激活」；**硬闸门维度闸门没过 → 整行不出现**。理由：用户没点它，列出来是多嘴。

**依据**：`AGENTS.md` 硬规矩 12。`tools/dim_check.py` 会检查「注册表标了闸门的维度，其入口 skill 的触发条件里必须有闸门」。

## 情形 C：从一本新书蒸馏（六步流水线）

### 你只需要两步
1. **把书发过来**：epub 最好；带文本层的 PDF 也行；扫描版先说一句是要「最准」还是「最快」。
2. 说一句「**按原书蒸馏，单独加一个维度**」。

### 我这边固定的六步

| 步 | 做什么 | 产物 |
|---|---|---|
| 1 取文本 | epub → 解 zip 读 XHTML；PDF → 抽文本层；**扫描版先找公版全文**（Project Gutenberg / archive.org 的同一译本，省 OCR、没错字、可逐字核引文）→ 找不到再 OCR（最准用 marker，最快用 rapidocr + pymupdf） | `sources/<书名>.txt` |
| 2 定风格卡 | 一本一张：R 节每条引文必须原书原话并给出处；A/E 的做法必须出自该书，自己的补充标「（补充）」；中文正文；不写 agent / 工具 / 模型专有名词；**外文原书**：R 节以英文原句逐字为准（真出处＝篇名＋年份），中文那行标「中译：」，不得声称逐字 | `distill/<family>/STYLE.md` |
| 3 蒸馏 | **数量由书的内容结构决定，不预设、不封顶**：书里有几个自成一体、能独立触发的方法/主题，就蒸几个 skill（一章一个、一个模型一个都行；薄书 2 个正常，厚书十几个也对）。不许为凑数硬拆，也不许为省事硬合。每个照 `templates/skill-template/` 九节写 + `test-prompts.json` 三类用例；可按章/主题分给多个子任务并行 | `skills/<前缀>-*/` |
| 4 回书核引文 | 每条 R 引文回原文核对（比对时归一化只留字母数字，避开排版差异误报）；核不过的删掉或改掉。**然后跑 `python tools/verify_citations.py`**：它一次核三件事——① 正文里的 `（R编号）` 指回是否都指得到 R 节真有的锚点（指空＝虚假依据）② 有源书的族（周易／八字／堪舆，源书在 `sources/`）R 节引文逐字回书核 ③ R 节是否完整（**自家规矩：R 节至少 3 条**，少于 3 条说明这个主题撑不起来，回去并进邻近 skill）。三项全 0 才算过 | 核验记录 |
| 5 登记维度 | 跑 `new_dimension.py`（即情形 B 的命令），把 skill 目录补进 `skills/` | 注册表 + hub |
| 6 装依赖 + 自检 + 升级 + 打包 | **先 `python tools/install_deps.py --install` 装依赖**，再 `python tools/dim_check.py`（0 错）→ **跑一次整包升级**（见下节）→ 打 zip | 成品包 |

### 判断标准（怎么算蒸馏出来了）
- 一个 skill 的 R 节**一条原书引文都没有** = 没蒸馏，只是自己的发挥，不算。
- 引文回书核不过 = 不算，必须删或改。
- 三条测试用例写不出「不应触发」的那条 = 触发条件没写清楚。
- **不设数量指标**：蒸馏几个 skill 只由书的内容结构决定。「3–5 个」这类数字不作要求，更不拿它当完成标准——凑数拆出来的 skill 一定触发不准，硬合出来的 skill 一定包不住。

### 骨架完备（缺一不可）

`skills/` 下除 `cross-system-hub`、`darwin-skill`、`zhengliu` 外的**每一个子 skill**，骨架必须完全一样，缺一不可：

- **frontmatter 四字段**：`name`、`description`、`input_schema`（含 `required`、`optional`）、`output_schema`（含 `primary`、`secondary`）。
- **正文十节**：`## 触发条件`、`## R：原文锚点`（也认 `## R —`／`## R 原文锚点`）、`## I：核心解释`、`## A1：来源应用`、`## A2：典型触发场景`、`## E：执行步骤`（也认 `执行步骤`）、`## B：边界与失败模式`（也认 `边界与失败`／`失败模式`）、`## 练习手册`（或 `练习`）、反例（`反例`）、灰色地带。
- **`test-prompts.json`**：必须存在，且含三类用例——应该触发 / 不应触发 / 边界。

**新书蒸馏、加维度、加 skill 一律照此**；`dim_check.py` 会逐项检查。老体系尚未补齐时缺项先作警告输出（含汇总行「骨架完备 x/184」）；补完后用 `STRICT_SKELETON=1 python tools/dim_check.py` 跑，缺项即硬错、退出码非 0。

## 收尾：先装依赖，再跑自检（三种情形都一样）

**依赖是自检前的一步**——skill 内容写完、注册表与 hub 补完之后，**先装依赖，再跑自检**（自检永远放在最后）。

**Python 依赖一律走国内源**（官方 pypi.org 在本环境拉不动）：

```bash
python tools/install_deps.py             # 体检：列出缺什么，不装
python tools/install_deps.py --install   # 缺什么装什么（清华源；装不动自动换阿里云）
python tools/dim_check.py                # 依赖装完，再来自检
```

依赖写两处，合并检查：

- 包根 `requirements.txt`（整包的依赖）；
- 每个 skill 的 frontmatter 可选字段（只有它自己需要的才写）：

```yaml
requires:
  pip: [pymeeus]        # pip 名（import 名不一样时脚本里有对照表）
  commands: [python3]   # 需要存在的可执行命令
```

**顺序：写 skill / 登记 / 补 hub → 装依赖 → 自检。** 装不上就先停下，把卡点写进说明，别硬往下走（跑不起来 = 没交付）。

**要联网取数的 skill：多一步「先查再跑」。** 数据源是**装不了**的依赖，只能先查连通。口径（与 AGENTS 硬规矩 11 同）：

1. 在 frontmatter 声明：`requires: { data: [<源名>] }`，源名必须是 `tools/install_deps.py` 里 `DATA_SOURCES` 登记过的；新源**先登记（含最小探针）再声明**。
2. 取数前跑体检：`python tools/install_deps.py`（含数据源探针，有不可用项退出码非 0），或该工具自带的 `--check`。**不许跑到一半才发现取不到。**
3. 探针要能识别「通但内容是坏的」——返回 200 不等于能用（实测：某 Overpass 实例时间戳非法、对任何地点都返回 0 条）。
4. 取不到就照实写：「取到 0 条」≠「现场没有」，回答里区分开。

**顺序变成：写 skill / 登记 / 补 hub → 装依赖 → 查数据源连通 → 跑数据 → 自检。**

需要编译的包在 Python 3.14 下常 build wheel 失败（实测 `pyswisseph`），优先挑**纯 Python** 的等价物（排盘用 `pymeeus`）。

## 每次蒸馏后必做：整包升级（判据：更准确、更能解决问题——**不唯分数**）

**约定：每蒸馏完一本书、新维度接入后，立刻跑一次整包升级。**
**升级的目的是让包更准确、更能解决问题。分数只是诊断工具，不是目标，也不设「必须过 N 分」这种阈值。**

做法（顺序固定）：

| 步 | 做什么 | 判据 |
|---|---|---|
| 1 备份 | 整包打逐文件 sha256 清单 + 实体副本 | 改动可证明回退 |
| 2 静态体检 | 跑代理尺扫 `skills/`（结构项：检查点、失败分支、反例、软化措辞、步骤数、引用可达） | 列出「待修」清单，逐条看是不是真问题 |
| 3 实测 | 抽一批 skill，**用全新输入**产出真实回答（不要用它自带的示例），交独立盲评审 | **两样都看**：① 绝对分（只当诊断）② **逐条读评委的「要点」**——信息量远大于分数 |
| 4 同题成对比较 | 改前／改后**同一道题**各出一份，**成对**交给评委，**不给分**、只问「哪一份更能解决问题、为什么」 | **这一步才是验收主判据** |
| 5 修 | 只修暴露的**真问题**（口径矛盾、缺分支、缺用例、说了「书里」却不给出处、自造零件名外露、推演看不见、行动不可勾）；**尺子误读的内容不改** | 复测确认 |
| 6 定版 | 版本号 +1，写进 hub 版本历史与 README | |

**为什么以成对比较为主**：绝对分换一批评委可摆动 ±0.9（实测：同一批 28 份旧族答卷，一次 7.843、一次 6.921；同材料、同尺子、同「3 评委取中位」的做法）。成对比较是**同一批评委在同一批里直接比两份**，把评委刻度差异抵掉了。

**五条「更准确、更能解决问题」的可勾判据**（读回答时逐条问，不看分数）：

1. 有没有**钉在这个人的具体事实上**（引他的话、说他的事），而不是通用话？
2. 推演**看得见**吗——结论能不能顺着读出来？
3. 行动**能不能今天/这周打勾**，有没有完成标准？
4. 边界守不守得住（不承诺结果、不替人拍板、缺信息就说缺什么）？
5. 有没有给出**可驳回的候选读解**让人自己去验？

四条底线：

- **不唯分数**：分数只作诊断，不许当验收目标；**也不许为了分数改尺子或改内容**。
- **升不到某个分数不算失败**：判据是「比上一版更准、更能解决问题」；量出来没变或变差，**如实报，不掩饰**。
- **分数只用独立测量**，包内自评不算数；尺子误读（例如把「建议就医」这类安全语当成软化措辞）时**改内容才是错**，如实记下来即可。
- **任何单点分数都要配误差**；跨轮比较一律以成对比较为主。

**取舍的优先级：好用 ＞ 准确 ＞ 分数。** 规矩多的时候冲突在所难免，按这个次序裁：

1. **好用（关键）**：读完能马上知道下一步做什么；行动能打勾；不啰嗦、不堆术语、不自造零件名。
2. **准确**：钉在这个人的事实上；**依据看得见**（引原书原句、或说明判据来自哪条框架与用户哪句原话——两种都算）；边界守得住。
3. **分数（锦上添花）**：在准确、好用的前提下分数更高最好；**绝不许为了分数牺牲前两条**。

**据此的一道取舍**：不要写「权重 ≥4 必须带原文锚点」这种**引书合规**式要求——它伤好用（逼出为引而引、答案变长变板），改成「**依据看得见**」；但「说了『书里』却不给出处」这类**表述不实**、和「自造零件名外露」这类**伤好用**的，照旧要修。

**看结果的一个反面教训（本轮实例）**：旧族实测只有 6.9–7.8，看着像「内容差」；但逐条读评委要点，28 份几乎全是「推演清楚／动作可打勾／边界守住，**但**无原书出处」。也就是说低分是**尺子把「有没有引书」当成高档的必要条件**造成的，不是分析力差。**先读要点、再谈修法**——否则很容易去修一个不是问题的问题。

## 元工具（zhengliu / darwin-skill）怎么算

它们**不是维度**：

| | 分析维度 | 元工具 |
|---|---|---|
| 进 hub 的维度概览表 | 进 | 不进 |
| 参与 STEP 1 激活扫描与排序 | 参与 | 不参与 |
| 登记在哪 | 注册表「正表」 | 注册表「元工具」表 |
| 干什么 | 分析用户的处境 | 维护这套包：`zhengliu` 把书蒸成 skill、`darwin-skill` 审计并优化 skill |

放的位置一样（都在 `skills/` 下、都能被加载、都能被触发），只是**身份不同**。加元工具：目录放进 `skills/` → 注册表「元工具」表加一行 → `python tools/dim_check.py`。

## 命令速查

| 目的 | 命令 |
|---|---|
| 加一个维度（建骨架 + 登记 + 补 hub + 自检） | `python tools/new_dimension.py --prefix … --name … --layer … --signals … --source … --skill …`（**前缀只写本体**，如 `ptolemy`，入口自动成 `ptolemy-*`） |
| 依赖体检 / 安装（国内源） | `python tools/install_deps.py` / `--install` |
| 一致性自检（0 错才算完） | `python tools/dim_check.py` |
| 先看要改什么、不落盘 | 上面两命令加 `--dry-run`（仅 new_dimension 支持） |

## 版本与回退

- **大改动前先打哈希清单**（逐文件 sha256），改完逐条比对——改动要可证明回退。
- 改了行为就升版本号，并写进 hub 的「版本历史」表与 README 的版本表。
- `history/` 放旧版本记录与已移除的 skill：**只作凭据，不参与输出**。
