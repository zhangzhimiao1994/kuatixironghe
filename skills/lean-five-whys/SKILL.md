# 五问（Five Whys）：找到根因，做比例投资，把组织调成自适应

**来源**：《The Lean Startup》CHAPTER 11 ADAPT（Part Three ACCELERATE）｜ 证据等级：firsthand

## 触发条件

**应该触发**：
- "同一个故障 / 投诉又出现了，上个月刚修过"
- "出了事故，复盘会开成了互相指责"
- "我该不该花时间建培训 / 基础设施 / 正式流程？"
- "项目总是延误，不知道卡在哪"
- "团队做事太快，老出低级错误"

**不应触发**：
- 用户问的是"该多久发一版 / 批次太大" → 走 `lean-small-batches`
- 用户问的是"增长为什么停了" → 走 `lean-engines-of-growth`
- 用户问的是"公司怎么搭创新团队" → 走 `lean-innovation-sandbox`
- 用户想借复盘开除 / 惩罚某人 → 🛑 不是追责工具
- 用户要法律 / 人事 / 财务判断 → 🛑 不做，指向专业人士

## R：原文锚点

> "The core idea of Five Whys is to tie investments directly to the prevention of the most problematic symptoms."（CHAPTER 11: ADAPT）（已据原文核）
> 中译：五问的核心思想，是把投入直接绑定到"预防最让人头疼的那类症候"上。

> "At the root of every seemingly technical problem is a human problem."（CHAPTER 11: ADAPT）（已据原文核）
> 中译：每一个看似技术性的问题，根子上都是人的问题。

> "the goal of the Five Whys is to help us see the objective truth that chronic problems are caused by bad process, not bad people, and remedy them accordingly."（CHAPTER 11: ADAPT）（已据原文核）
> 中译：五问的目标，是帮我们看到一个客观真相——长期反复的问题源于糟糕的流程，而不是坏人，并据此去补救。

> "Be tolerant of all mistakes the first time. 2. Never allow the same mistake to be made twice."（CHAPTER 11: ADAPT）（已据原文核）
> 中译（简化版的两条规则）：一、第一次犯任何错都宽容；二、绝不允许同一个错犯第二次。

> "you cannot trade quality for time."（CHAPTER 11: ADAPT）（已据原文核）
> 中译：你不能用质量去换时间。

## I：核心解释

1. **自适应组织**：能自动把流程和表现调整到当前条件的组织。创业长大需要加流程，但加错了就变僵化官僚——五问是那个"刚刚好"的调节器。
2. **五问核心**：不是空谈根因，而是把投入直接绑到"预防最痛的症候"上。问题反复出现、每次都痛，才值得持续投资去根除。（R1）
3. **根因常是人的问题**：Ohno 的机器停转例里，从"保险丝烧了"一路问到"没人装滤网"；IMVU 的例子从"服务器故障"问到"经理觉得培训浪费时间"。技术故障背后往往是培训或流程缺口。（R2）
4. **比例投资**：在五个层级上，每一层都做一个与症状严重度成比例的投资——症状轻就小投入，症状重才大投入。先做"八周计划的第一小时"，问题再犯就继续推进。（R3）
5. **自动调速器**：问题越多 → 投入预防越多 → 危机越少 → 团队重新变快。它防止团队"太快"而拿质量换时间。（R3）
6. **五责（Five Blames）**：五问失败的样子——互相指人。解药：让所有受影响的人都在场（漏掉谁，谁就成了替罪羊）；最高层说"如果这错这么容易犯，是我们丢人"；用系统视角。（R4）
7. **起步规则**：先用简化两条规则（宽容第一次 / 不许重犯）；从小而具体的一类症候开始；触发规则要简单、铁定、无歧义；指定一名"五问 master"。
8. **别把积压的"行李"一次拖进来**：五问要跟着新出现的问题做，旧账会在过程中自然浮现、被逐步修掉；没浮现的，也许没想象中那么大。

## A1：来源应用 — 书里给的具体做法

- **Ohno 的示例**：机器停 → 过载烧保险丝 → 轴承没润滑 → 润滑泵不打油 → 泵轴磨损 → 没装滤网进了金属屑；不问到底就只会换保险丝，问题几个月后再来。
- **IMVU 培训例**：发布故障 → 服务器挂 → 子系统用错 → 工程师不会用 → 没受训 → 经理"太忙"不信培训。于是从"先花第一小时"开始，逐步长出培训体系，新人第一天就能干活。
- **比例投资实例（IGN 侧栏）**：API 500 错误 → gem 不兼容 → 多加了新版本 gem → 生产未测 → 提前装不需要的 gem → 周五晚改生产；对应投资是改 CMS 更容错、换 bundler、补测试、自动化 gem 管理、禁止周五改生产。
- **两条简化规则**：宽容第一次 / 不许重犯。
- **指派五问 master**：moderator、决定预防步骤、分派跟进；要够资深能推动、又不能资深到没空参会。

## A2：典型触发场景

- 同一类事故 / 客户投诉反复发生
- 复盘会变成甩锅大会
- 纠结"要不要投资培训 / 流程 / 基础设施"
- 项目反复延误、团队抱怨"太忙没时间复盘"
- 小改动引发大事故后，想知道根因

## E：执行步骤

### 步骤1：确认环境是否具备
**输入**：组织是否有信任、赋权、高层支持。
**输出**：判断能否做完整五问，还是先用简化版。
🔴 **CHECKPOINT — 触发条件：缺高层支持或不信任**：只用两条简化规则在个人 / 小范围自我演练（"我怎样确保不再陷入这处境？"），或暂停，别硬推。

### 步骤2：选小而具体的一类症候 + 铁定触发规则
**输入**：当前的一堆问题。
**输出**：挑一类具体、量小到"每次发生都开得起会"的症候，定一条简单无歧义的触发规则。
🔴 **CHECKPOINT — 触发条件：用户想一上来就解决最痛的大事 / 一堆旧账**：劝退——高 stakes 最容易变五责，先在小事上练熟流程。

### 步骤3：走五问，每层做比例投资
**输入**：该症候的一次具体发生。
**输出**：一条根因链 + 每一层的比例投资清单。
照 R1 / R3：每层投入与严重度成正比。

### 步骤4：指定 master，跟踪跟进
**输入**：会议的决策与分派。
**输出**：一位五问 master 负责推进与验收预防措施。

### 步骤5：防五责、守系统视角
**输入**：过程中是否出现指责。
**输出**：所有人到场 + 系统视角的结论（坏流程，不是坏人）。
🔴 **CHECKPOINT — 触发条件：出现互相指责 / 用户想借此追责**：拉回——五问不是追责工具，目标是"这个问题为什么这么容易发生"。（R4）

## 输出纪律（回答硬要求）

以下每条都是写回答时的硬要求，违反任一条就重写：

1. **先用他自己的细节复述处境**：开头不摆方法、定义或框架，先用他给的产品/团队/数字，把他那句话讲回去。
   - ❌ 模板开头：五问是一种连续追问五个为什么、定位根因的方法……
   - ✅ 贴合开头：同一个客诉这一季已经第四次了，复盘每次开成"到底谁的锅"——要找的不是谁，而是这件事为什么这么容易再发生。
2. **判断落在他的具体事实上**：结论要能指到他说的那个数字、环节或那句话上；换个人、换个问题，骨架必须跟着变——**两份回答的结构能对调，就是失败**。
3. **不向用户抖术语或结构名**：MVP、最小可行产品、创新核算、增长引擎、五问、沙盒、信仰之跃这类词不直接甩给用户；真要讲，先用大白话说清意思，再看要不要带名字。
4. **正文 ≤800 字**，短、准，不铺排。
5. **结尾给一个今天或这周能做、能打勾的动作**。
6. **涉钱、法律、团队的决定只给倾向和办法，不替他拍板**；必要处明确提示找律师／税师／专业顾问。

## B：边界与失败模式

| 情况 | 表现 | 怎么处理 |
|------|------|---------|
| 对不同人复用同一骨架 | 换个用户、换个问题，回答结构原样照搬 | 用他自己的数字、产品、原话重写开头与结论，结构与处境绑定 |
| 向用户抖术语 / 结构名 | 张嘴就是 MVP、创新核算、五问、沙盒 | 先用大白话说清意思，必要时才带名字 |
| 变成五责 | "都是那个基层员工干的" | 🛑 慢性问题是坏流程；所有人到场 + 系统视角。 |
| 高 stakes 硬推 | 首会就翻车 | 🔴 从小而具体、低风险处起步。 |
| 缺高层支持仍强推 | 结论没人执行 | 🛑 改用简化两条规则，或等条件成熟。 |
| 把五问当追责 / 开除工具 | "查出是谁干的" | 🛑 不是追责工具；目标是不再重犯。 |
| 一次拖进所有旧账 | 会开不完、无结论 | 🔴 跟着新问题做，旧账自然浮现再修。 |
| 替用户做人事 / 经营决定 | "那就裁了那个经理" | 🛑 不做人事 / 经营决定。 |

**边界规则**：
1. 五问针对"流程 / 系统"，不针对个人追责。
2. 比例投资的原则是不轻率大投入，也不放任小问题。
3. 需要高层支持才能持久；个人只能先用简化版。
4. 不替用户做人事、经营、法律、财务决定。

**用户自查清单**：
- [ ] 我确认了环境 / 是否该用简化版
- [ ] 我选的是小而具体的症候，不是一堆旧账
- [ ] 每一层都做了与严重度成比例的投资
- [ ] 所有受影响的人都在场，没人在场外当替罪羊
- [ ] 我没有把它变成追责或人事手段

**安全兜底**：涉及人身安全、心理危机或法规风险的事故，本 skill 只做流程复盘，不替代安全隐患排查、劳动保护、律师或心理支持，须指向对应专业资源。

## 📖 练习手册

**五问推演**：拿"某功能突然挂掉"当假想症候，自己写一条五问链，每层配一个"比例投资"，体会从技术故障收敛到流程 / 人的过程。

**五责识别**：回想一次开成"互相指责"的复盘会，用书里的两条解药（所有人到场、系统视角）改写会议规则。

## 🚫 反例黑名单

1. **把五问开成五责** → 🛑 慢性问题是坏流程。
2. **用五问追责 / 开人** → 🛑 不是这个工具。
3. **一开始就啃最痛的大事** → 🔴 先练熟流程。
4. **缺信任缺授权还硬推** → 🛑 只能用简化版。
5. **把投入当报复性大改造** → 🔴 比例投资，先做第一小时。

### 灰色地带

- **组织明确不信任、五问会变成批斗**：书里承认这种情形五问会被压垮；只能退到两条简化规则，或先改善信任。
- **个人贡献者想推但拿不到授权**：书里建议谨慎，可用简化版；完整的五问需要能拍板的人在场。
- **事故既有人为疏忽也有系统缺陷**：系统视角不等于免去个人责任，书里的重心是"让它难以再犯"，不是替谁开脱——具体如何问责超出本 skill，需按组织制度处理。
