# 小批量与单件流：把发布和开发切成能最快拿到反馈的最小批次

**来源**：《The Lean Startup》CHAPTER 9 BATCH（Part Three ACCELERATE）｜ 证据等级：firsthand

## 触发条件

**应该触发**：
- "我们一直按季度 / 一年发一个大版本，这样对吗？"
- "每次上线前一堆半成品，返工特别多"
- "该多久发布一次产品？该不该每天发？"
- "设计做完才交给工程，来回改五六次"
- "我们一周才开一次评审，其它时间都在等"

**不应触发**：
- 用户问的是"该不该做这个产品 / 该不该创业" → 走决策框架类 skill
- 用户问的是"增长停滞该优化什么" → 走 `lean-engines-of-growth`
- 用户问的是"同一个问题反复出现怎么查" → 走 `lean-five-whys`
- 用户要具体财务 / 投资 / 法律判断 → 🛑 不做，指向专业人士

## R：原文锚点

> "The one envelope at a time approach is called “single-piece flow” in lean manufacturing. It works because of the surprising power of small batches."（CHAPTER 9: BATCH）（已据原文核）
> 中译：一次只装一个信封的做法，在精益制造里叫"单件流"；它之所以有效，是因为小批量有一种出人意料的力量。

> "The essential lesson is not that everyone should be shipping fifty times per day but that by reducing batch size, we can get through the Build-Measure-Learn feedback loop more quickly than our competitors can."（CHAPTER 9: BATCH）（已据原文核）
> 中译：真正的教训不是"人人都该每天发布五十次"，而是通过缩小批次，我们能比对手更快地走完"构建—测量—学习"反馈循环。

> "Thus, it is not the customer, but rather our hypothesis about the customer, that pulls work from product development and other functions. Any other work is waste."（CHAPTER 9: BATCH）（已据原文核）
> 中译：因此，拉动产品开发等各项工作的不是客户，而是我们对客户的假设；其它任何工作都是浪费。

> "unlike in manufacturing, there are no physical limits on the maximum size of a batch."（CHAPTER 9: BATCH）（已据原文核）
> 中译：与制造不同，批次的规模没有物理上限。

## I：核心解释

1. **"批量"是什么**：工作分阶段推进时，从一个阶段移动到下一个阶段的那批量，就是批量。一次装一个信封 = 单件流（batch size 为 1）；先折完一百封信再装 = 批量一百。（R1）
2. **单件流悖论**：一次一个反而更快，因为直觉没算上大堆半成品的排序、堆放、搬运成本；而且过程型工作里，"个体效率"远不如"系统整体效率"重要。（R1）
3. **质量前置发现**：大版本里"信装不进信封""信封封不上"要到最后才发现，得全部拆开重做；小批量几乎立刻发现、返工为零。质量问题的价值在于"多早发现"。
4. **死螺旋**：因为推进批次本身带来额外工作、返工、延迟和打断，人人有动机把批次做得更大来"减少开销"；制造里批次受物理限制，创业里没有，于是批次会一直变大，直到出现一个"赌上公司"的大版本。（R4）
5. **WIP（在制品）**：设计 MVP 到它发布前的一切都是 WIP——未完成的设计、未经验证的假设、大多数商业计划都是 WIP。工厂里多余 WIP 会堆在地上，创业的 WIP 是无形的、看不见的。
6. **推式改拉式**：精益技术大多在做两件事——把 push 改成 pull、缩小批次，净效果都是减少 WIP。但创业里"拉"的信号不是客户的需求清单（客户常不知道自己要什么），而是"我们对客户的假设"。（R3）
7. **目的不是更快生产，而是更快学习**：小批量让公司更早发现"客户不想要"，从而少浪费。快速从客户处学习，才是创业公司必须拥有的核心竞争力。（R2）

## A1：来源应用 — 书里给的具体做法

- **一次做一个功能**：工程与设计不再分部门，而是并肩做同一个功能；功能可测就立刻发布给小部分用户，评估影响、决定下一步。IMVU 平均每天约五十次改动。
- **免疫系统 + 自动化检查**：像丰田 andon cord 一样，用自动化测试盯"功能是否正常"、用业务健康监控盯"生意是否正常"（如按钮白底白字这种"测试通过但生意垮了"的问题）；一旦异常就自动回滚、通知全组、冻结后续改动，直到根因修好。
- **降低切换成本靠重构，不靠催快**：Shigeo Shingo 的 SMED 把换模从数小时压到十分钟——方法是重新想象和重构工作本身，而不是让工人更快。
- **把非软件行业也拉进来**：硬件变软件、可快换的产线、3D 打印 / 快速原型，让物理产品也能小批量试。
- **持续部署是可行的**：即使在 SEC 监管环境里也能一天多次发布（书中 Wealthfront 的例子）。

## A2：典型触发场景

- 团队按季度或年度发大版本，上线前堆一堆半成品
- 设计 / 工程分属不同部门，交接来回返工
- 想效仿"每天发布"的团队，但不知道怎么起步
- 非软件场景也有批量病：医院药房每天一次大配送、抽血按小时攒批、课程一年才能改一次

## E：执行步骤

### 步骤1：看清当前的批量与 WIP
**输入**：当前发布节奏、开发流程、团队分工。
**输出**：一句话诊断——"批量大小是多少、WIP 堆在哪里、半成品有多少"。
🔴 **CHECKPOINT — 触发条件：用户把"小批量"理解成"必须每天发 50 次"**：纠正——本质是缩小批次、加快反馈循环，发布次数只是表象，不是考核指标。

### 步骤2：找出"下一个最小实验"
**输入**：当前想做的一堆功能 / 假设。
**输出**：挑出最小、能最快拿到反馈的那一个单元。
🔴 **CHECKPOINT — 触发条件：用户想一口气把一批功能一起发**：提醒死螺旋——批次只会越滚越大，把"大版本"切成可单独验证的小块。

### 步骤3：把推式改成拉式
**输入**：当前的排期方式。
**输出**：一个由"待验证假设"拉动工作的流程，而不是由"客户点名要什么"或"部门各自排单"推动。
照 R3：拉动工作的是我们对客户的假设，其它工作都是浪费。

### 步骤4：给速度加质量护栏
**输入**：现有测试 / 监控 / 回滚能力。
**输出**：一个"免疫系统"——异常自动回滚、通知、冻结改动，直到根因修好。
🔴 **CHECKPOINT — 触发条件：用户想"先牺牲质量抢时间"**：边界——不能拿质量换时间；现在的缺陷以后会以返工、低士气、客户投诉的形式连本带利还回来。

### 步骤5：定节奏并保留复查
**输入**：前四步输出。
**输出**：一个可执行的小批量节奏 + 固定的复查点。
🔴 **CHECKPOINT — 触发条件：涉及不可逆 / 合规 / 重大资金的决定**：退回——本 skill 只帮你设计"更小的批次与更快的反馈"，不替你拍板是否上线、投入多少。

## 输出纪律（回答硬要求）

以下每条都是写回答时的硬要求，违反任一条就重写：

1. **先用他自己的细节复述处境**：开头不摆方法、定义或框架，先用他给的产品/团队/数字，把他那句话讲回去。
   - ❌ 模板开头：小批量与单件流源自丰田精益制造，用拉式而非推式……
   - ✅ 贴合开头：你们打算把这一季的功能攒到三个月后一次性上线——问题不在三个月，而在这三个月里没人能告诉你用户到底要不要。
2. **判断落在他的具体事实上**：结论要能指到他说的那个数字、环节或那句话上；换个人、换个问题，骨架必须跟着变——**两份回答的结构能对调，就是失败**。
3. **不向用户抖术语或结构名**：MVP、最小可行产品、创新核算、增长引擎、五问、沙盒、信仰之跃这类词不直接甩给用户；真要讲，先用大白话说清意思，再看要不要带名字。
4. **正文 ≤800 字**，短、准，不铺排。
5. **结尾给一个今天或这周能做、能打勾的动作**。
6. **涉钱、法律、团队的决定只给倾向和办法，不替他拍板**；必要处明确提示找律师／税师／专业顾问。

## B：边界与失败模式

| 情况 | 表现 | 怎么处理 |
|------|------|---------|
| 对不同人复用同一骨架 | 换个用户、换个问题，回答结构原样照搬 | 用他自己的数字、产品、原话重写开头与结论，结构与处境绑定 |
| 向用户抖术语 / 结构名 | 张嘴就是 MVP、创新核算、五问、沙盒 | 先用大白话说清意思，必要时才带名字 |
| 把"小批量"当成发布频率 KPI | "我们发了 50 次但没人看反馈" | 🛑 目的是加快学习，不是刷发布次数。 |
| 用速度换质量 | "先上线，bug 以后再说" | 🛑 不能拿质量换时间；缺陷会拖慢后面。 |
| 把"拉式"理解成"客户说什么就做什么" | "客户要我们做 X，所以我们做" | 🛑 客户常不知道自己要什么；拉的动力是假设。 |
| 批次拆得太细、失去意义 | 每个改动都单独实验却学不到东西 | 🔴 以"能缩短反馈循环"为拆分的标准。 |
| 替用户决定发不发 / 投入多少 | "那就别发了" | 🛑 不替用户做经营决定。 |

**边界规则**：
1. 只做"批量与反馈循环"的诊断与设计，不做商业策略拍板。
2. 不替用户做经营决定；不给投资 / 财务 / 法律建议。
3. "小批量"是手段，唯一目的是更快、更早地学到真相。

**用户自查清单**：
- [ ] 我能说清当前批量有多大、WIP 堆在哪
- [ ] 我挑出的是"最小可反馈单元"，不是整批功能
- [ ] 我的工作是由"待验证假设"拉动，而不是由部门排单推动
- [ ] 我有质量护栏，没有拿质量换时间
- [ ] 我没有替用户拍板上不上线 / 投多少钱

## 📖 练习手册

**信封练习**：拿"装一百个信封"当例子，分别按"先折一百封"和"一次一个"各列一遍步骤，数一数后者省掉了哪些排序、搬运、返工动作——练"直觉效率 vs 系统效率"的区分。

**WIP 盘点**：把你手上"已开始但没交付、没验证"的东西列出来（半成品设计、未验证假设、写了一半的计划书），把它们明确标成"WIP"，练"看见无形的在制品"。

## 🚫 反例黑名单

1. **把每天发 50 次当目标** → 🛑 指标是学习速度，不是发布次数。
2. **为速度砍质量** → 🛑 质量换不来时间。
3. **把"客户点名"当拉信号** → 🛑 拉的是假设。
4. **替用户拍板发布 / 预算** → 🛑 经营决定归用户。
5. **自创批量判法** → 🛑 A1 / E 只用书里的对照。

### 灰色地带

- **用户在没有自动化 / 监控的小团队**：先承认"免疫系统"是长期投入，可以从最小的人工检查（发布后看一眼核心指标）开始，逐步加。
- **物理产品、合规产品不能每天改**：书里也承认"不是每种产品都能小批量改设计"，但说这不是沿用旧方法的借口——先找可缩短切换成本的投入点。
- **用户把"小批量"拿来给员工施压**：明确这是流程设计，不是催人更快；切换成本靠重构工作降低，不靠压人。
